# 工程规范

## 架构

Novro 采用可维护的单仓库和模块化单体：根目录管理统一工具与文档，Go
服务负责认证、业务规则和数据访问，`apps/web` 中的 Next.js 应用负责控制台。
业务模块在同一进程内保持清晰边界，第一版不拆分微服务。

```text
novro/
├── cmd/novro/          # Go 服务唯一入口
├── internal/           # 配置、HTTP、认证和用户模块
├── ent/                # Ent Schema 与生成代码
│   └── migrate/        # 可审查、按序执行的 SQL 迁移
├── apps/web/           # Next.js 控制台
├── design/             # 页面结构、视觉和交互资料
├── scripts/            # 本地开发和检查脚本
└── docs/               # 产品与工程文档
```

领域目录按实际能力创建，余额、支付、API Key、模型网关、模型路由和供应商模块分别放在
`internal/<domain>` 包中，不拆出网络服务，不改变模块化单体布局。

当前已完成范围以 `docs/roadmap.md` 为准。支付范围目前只包含易支付风格网关的余额充值；
套餐、订阅、优惠券、组织、项目、复杂提供商编排、多区域部署和微服务拆分不在当前范围内，
只有后续路线图明确纳入后才开始实现。

## 质量门槛

每个阶段只提交已经通过对应检查的代码。完整交付前运行 Go 测试和静态检查，
以及前端 lint、类型检查、测试和生产构建。认证、权限、最后一个管理员保护、
配置错误和数据库不可用等关键路径必须有自动化测试。

## 配置与秘密

应用只读取环境变量。仓库只保留无秘密的 `.env.example`，真实 `.env`、数据库
密码、会话令牌、供应商密钥和支付商户密钥都不得进入 Git、日志或浏览器资源。MySQL 管理员
账号只允许用于受控初始化；服务运行必须使用最小权限的专用账号。

## 数据库变更

Ent Schema 表达应用模型，`ent/migrate` 保存实际部署的版本化 SQL。服务启动时使用
版本化迁移器核对历史校验和并补齐未执行文件，不使用 Ent 自动建表。显式迁移命令仍
用于部署前主动执行，并在发布前完成审查和 MySQL 验证。
涉及多个写操作或业务不变量的变更必须放在同一事务内。

## API 与错误

控制台 API 使用 `/api` 前缀，模型兼容 API 使用 `/v1` 前缀。错误响应使用
稳定的错误代码和面向用户的信息，不返回 SQL、内部地址、堆栈或秘密值。日志使用
结构化字段并带请求 ID，但禁止记录认证头、Cookie 和密码字段。

## Git 工作方式

开发按可验证阶段提交。提交前检查暂存内容和秘密；生成代码必须可由仓库内命令
重建，数据库迁移则作为需要人工审查的源文件提交。
